- **Реализовано и доказано на 31.08.2026.** Компонент существует в текущем

## Техническое резюме

Рекомендуемая система — не «LLM, который придумывает режимы скважин», а
проверяемый агентный цифровой двойник. Языковая модель диагностирует ситуацию,
выбирает стратегию поиска, вызывает разрешённые инструменты и объясняет решение.
Все численные расчёты, ограничения, формирование wells_schedule.inc и ЧДД
выполняются детерминированными компонентами.

Дополнительное архитектурное решение для Track 1 — **агентное управление с
сертификацией каждого принятого шага полной ГДМ**:

1. агенты анализируют текущее состояние и формируют типизированные намерения;
2. численный оптимизатор строит небольшой набор допустимых кандидатов;
3. существующий контур TimesOil — CRM, CRM2P, CRMP, Джентил и обучаемые
   модели — отсеивает явно слабые варианты;
4. полная ГДМ рассчитывает оставшиеся варианты;
5. официальный расчётчик ЧДД оценивает траектории;
6. защитный контур принимает только физически допустимое действие;
7. первый месяц принятого плана добавляется в расписание; после КТ2 состояние
   должно браться из бинарного restart полной ГДМ и цикл должен повторяться.

На КТ2 реализован source-bound первый шаг этого цикла: два варианта января 2014
пересчитаны полным replay от исходного deck до 01.02.2014. No-op дал
`110,782383361`, alternative — `110,776225880` млн руб. Бинарный restart не
использовался, поэтому результат нельзя выдавать за многомесячный MPC.

Для Track 2 меняется модель мира. Реализованный вариант КТ2 — **не временная
графовая нейросеть**, а компактный гибрид: CRM/материальный баланс как
детерминированный переход плюс ансамбль LightGBM, который прогнозирует остатки
нефти, жидкости и давления. Ансамблевое расхождение и выход признаков за
обучающий диапазон образуют fail-closed OOD gate. Training v3 и proxy-search v3
завершены; baseline выбран среди 32 принятых кандидатов. Финальный план обязан
пройти полную ГДМ и официальный ЧДД. Этот gate закрыт: baseline воспроизведён в
OPM, а `operational_sunk_assets` дал ЧДД `11918,789227263` млн руб. Результат
self-authenticated, но не сертифицирован организаторами.

Единая формула архитектуры:

~~~text
Case → State → Intent → Feasible Action → World Model → Trajectory
     → Official Economics → Risk Gate → Schedule → Evidence
~~~

Реализации World Model:

- Track 1: GdmWorldModel — полная ГДМ в каждом принятом шаге;
- Track 2: SurrogateWorldModel — быстрый поиск, затем GdmValidator.

### Критическая особенность расчётчика ЧДД

Обязательный вход содержит 14 полей:

DATA, well, WLPT, WLPR, WOMT, WOMR, WWIR, WWIT, THP, BHP, WEFF,
WLPT_Diff, WOMT_Diff, WWIT_Diff.

Значимые правила:

- нефть и жидкость передаются в тоннах, закачка — в м³;
- WLPR выше 500 — фатальная ошибка;
- отрицательное значение хотя бы одного из трёх полей Diff исключает всю
  скважино-месячную строку из экономики;
- стартовый год необходимо задавать явно;
- вызов без start-year начинает расчёт с минимального года данных.

Поставленный ранее JSON для Track 2 рассчитан с 1991-01-01 и даёт
4418,132 млн руб.; он не является контрольным значением новой траектории.
Реализованный `CHDDEconomicsAdapter` запрещает неявный `start_year`, сохраняет
его в manifest и отдельно фиксирует профиль `chargeInitialPump`.

Новые базовые файлы от 31.08.2026 дают последние значения накопленного ЧДД:

- Model Y: 5326,453 млн руб. в OPM Flow и 5261,159 млн руб. в tNavigator;
- Model Z: 5157,016 млн руб. в OPM Flow и 5218,945 млн руб. в tNavigator.

Полноисторический Model Z OPM→CHDD с профилем организатора
`chargeInitialPump=true` дал 5181,184 млн руб.: отклонение от OPM-эталона
24,168 млн руб. (0,469%) находится внутри опубликованного межсимуляторного
диапазона 61,929 млн руб. Для оптимизационного горизонта используется
`chargeInitialPump=false`, потому что существующие насосы являются sunk assets;
это правило записывается в provenance и не подбирается под ЧДД.

## Архитектурные принципы

### 1. LLM не является численным источником истины

LLM может:

- интерпретировать состояние и ограничения;
- выбирать шаблон стратегии;
- вызывать только разрешённые инструменты;
- сравнивать подтверждённые варианты;
- формировать объяснение из численных фактов.

LLM не может:

- придумывать значения дебитов, давления или ЧДД;
- напрямую писать deck или wells_schedule.inc;
- изменять пределы безопасности;
- выполнять shell-команды;
- обходить неуспешную проверку;
- объявлять план финальным без ГДМ и CHDD.

### 2. Каждая граница — типизированный контракт

Численный доменный контур использует неизменяемые frozen dataclasses:
`Case`, `State`, `ControlAction`, `Trajectory`, `Economics` и `Evidence`.
Pydantic используется только на FastAPI-границе для request/response-моделей;
он не является реализацией внутренних domain contracts.

Свободный текст хранится только как пояснение и никогда не управляет
симулятором.

### 3. Жёсткие ограничения не заменяются штрафами

Проекция допустимости выполняется до запуска модели мира. После расчёта
отдельный защитный контур проверяет:

- существование и тип скважины;
- даты и порядок событий;
- допустимые режимы и единицы;
- пределы жидкости, закачки и давления;
- фонд, остановки, пуски и переводы;
- неотрицательность месячных приращений;
- монотонность накопленных показателей;
- parser round-trip расписания.

Штрафы разрешены только для мягких предпочтений. Нарушитель жёсткого
ограничения не участвует в ранжировании.

### 4. Полная происхождаемость результата

Каждый результат связывается с:

- хэшем исходного deck;
- хэшем overlay и ограничений;
- Git commit;
- uv.lock;
- версией контейнера OPM/tNavigator;
- версией модели и tokenizer;
- seed;
- конфигурацией оптимизатора;
- версией CHDD и явным start date;
- хэшами trajectory, schedule и отчёта.

## Общая архитектура двух треков

~~~mermaid
flowchart TD
    A[Исходный deck + тестовый кейс] --> B[Case Loader]
    B --> C[Валидатор схемы, единиц и ограничений]
    C --> D[Каноническое состояние]
    D --> E[Детерминированный AgentWorkflow: 4 роли]
    E --> F[Типизированные намерения]
    F --> G[Проекция в допустимое пространство]
    G --> H[Численный генератор кандидатов]

    H --> I1[Track 1: CRM/TimesOil prescreen]
    I1 --> J1[Полная ГДМ для каждого финалиста]

    H --> I2[Track 2: физический baseline + LightGBM residual ensemble]
    I2 --> J2[UQ/OOD gate]
    J2 --> K2[Полная ГДМ для top-K и финала]

    J1 --> L[Извлечение 14 полей]
    K2 --> L
    L --> M[Официальный CHDD]
    M --> N[Constraint + Risk Gate]
    N --> O[Компилятор wells_schedule.inc]
    O --> P[Round-trip parser]
    P --> Q[Финальный replay]
    Q --> R[Evidence bundle + UI + выгрузка]

    S[Qwen через OpenAI API] --> E
    T[JSON manifests + SHA-256 receipts] -. трассировка .-> E
    T -. артефакты .-> R
~~~

### Общие сервисы

1. **Case service.** Распаковывает кейс в неизменяемую рабочую область,
   вычисляет хэши, читает deck и накладывает разрешённый overlay.
2. **Constraint service.** Единственное место определения физических,
   технологических и конкурсных ограничений.
3. **Simulator adapter.** Единый интерфейс к OPM Flow и, при доступности,
   tNavigator.
4. **Economics adapter.** Всегда вызывает официальный CHDD с явной датой.
5. **Schedule compiler.** Генерирует Eclipse/OPM-синтаксис только из
   валидированного ControlPlan.
6. **Agent control plane.** Управляет этапами, но не дублирует численные
   алгоритмы.
7. **Evidence service.** Собирает проверяемые основания решения.
8. **UI/API.** Текущий FastAPI-фасад даёт health/capabilities, агентный
   эксперимент, CHDD и встроенную операторскую страницу. Полный запуск треков
   через jobs относится к целевой архитектуре после КТ2.

## Аудит существующего TimesOil

### Итоговая граница зрелости

TimesOil — не заготовка «с нуля». В репозитории уже есть зрелый исследовательский
контур шестимесячного прогноза Model Y:

~~~text
Excel/CSV Model Y
  → нормализация и контроль качества
  → фонд, блоки и адресная связность
  → CRM / CRM2P / CRMP / Джентил
  → LightGBM / Chronos-2 / TiRex-2 / TiDE
  → ансамбль и конформные интервалы
  → прокси-оптимизация постоянной закачки SLSQP
  → CSV, графики и PDF
~~~

Эта схема описывает исходный прогнозный слой. Текущий репозиторий дополнительно
содержит `src/timesoil/aios`: он запускает OPM Flow в изолированных каталогах,
извлекает SUMMARY, формирует 14 полей, вызывает официальный CHDD, компилирует и
повторно читает `wells_schedule.inc`. Корректное разделение ролей теперь такое:

- Track 1 — быстрый предварительный отсев и диагностика перед обязательной
  полной ГДМ;
- Track 2 — реализованный физический baseline и LightGBM residual ensemble,
  обучаемый только на проверенных целых OPM-траекториях Model Z;
- ни в одном треке — не источник финальной сертификации плана.

Далее используются три разных статуса, которые нельзя смешивать:

- **реализовано в коде** — функция или сценарий существует;
- **численно подтверждено** — результат прямо пересчитан по текущему CSV либо
  найден в совпадающем локальном/серверном артефакте;
- **готово к демонстрации КТ2** — компонент включён в воспроизводимый цикл с
  контрактами, хэшами и проверяемым артефактом. Baseline и ограниченный
  одношаговый Track 1 этому определению соответствуют; полные конкурсные
  решения обоих треков — нет.

### Данные и вычислительные контракты

- канонический длинный формат date × well с нефтью, жидкостью, закачкой,

### Остаточный долг воспроизводимости

1. Исследовательские `run_ensemble`/`run_stacking` всё ещё могут зависеть от
   внешнего `results`; они не входят в доказательство AIOS КТ2.
2. Бинарный restart OPM для Model Y не реализован: текущий Track 1 backend
   воспроизводит deck полностью до одной месячной границы.
3. Четыре Model Z OPM-траектории — минимальный демонстрационный набор, а не
   достаточная выборка для заявления production-обобщения.
4. API честно сообщает `certified=false`; `model_z_trained=false` означает,
   что в минимальный API runtime не примонтирован доказанный A100-артефакт
   training v3, а не что обучение не выполнялось.
5. Docker v5 подтверждает terminal API image и runtime/security gates, но не
   Qwen workflow/connectivity и не загрузку внешней Model Z.
6. GPU не используются для OPM; все вычисления Flow идут последовательно на
   CPU, не затрагивая production-процессы на A100.
7. Первая финальная replay-попытка остановилась на общем 64 MiB evidence-cap
   после успешного OPM/export и до ЧДД. Failure receipt сохранён; единственный
   scoped cap-fix и успешный повтор аутентифицированы отдельным audit.

### Решение о повторном использовании

| Слой | Track 1 | Track 2 |
|---|---|---|
| data/wells | обернуть в CaseAdapter Model Y | использовать только шаблон; идентификаторы Model Y не переносить |
| CRM/CRM2P/CRMP/Джентил | предварительный отсев и диагностика | физический baseline нового суррогата |
| allocation/gains | проектор закачки и признаки блоков | признаки физического baseline и ограничений управления |
| mlprep | признаки historical/future-known | основа нового trajectory feature builder |
| scenario augmentation | проверка устойчивости Model Y | прототип обучения по сценариям, переписать для Model Z |
| LightGBM/TSFM | дешёвое ранжирование, не сертификация | LightGBM — текущая residual-модель; TSFM — только benchmark |
| ансамбли/crepes | диагностические интервалы | ансамблевое расхождение и OOD; conformal — после КТ2 |
| SLSQP | локальная доводка закачки после проекции | локальная доводка непрерывной части плана |

Главное правило интеграции: существующие функции не переписывать без причины,

фонд, блоки и параметры Model Y в Model Z.

## Track 1 — дополнительная source-bound архитектура

### Целевая схема: Full-Physics-Certified Agentic MPC

После КТ2 Track 1 следует развивать как иерархическое модельно-прогнозирующее
управление. На каждом месяце оптимизируется короткий горизонт, но в итоговое
расписание фиксируется только первый шаг. Новое состояние берётся из полной
ГДМ, а не из CRM или LLM.

~~~text
restart_t
  → диагностика состояния
  → предложения агентов
  → допустимые кандидаты
  → CRM/CRMP/Джентил prescreen
  → полная ГДМ кандидатов
  → официальный ЧДД
  → защитный критик
  → принять действие месяца t
  → restart_t+1
  → повторить
~~~

Это одновременно выполняет требование о полной ГДМ в цикле и сохраняет
реалистичный вычислительный бюджет.

**Реализовано и доказано на КТ2:** `MonthlyMPC` и строгие контракты поддерживают
последовательность месяцев, но реальный `OpmFullReplayBackend` доказан только
для января 2014. Он выполняет полный replay deck, обрезанный после 01.02.2014,
то есть `binary_restart=false`. Два кандидата отличались только закачкой
скважины 2: 140 против 150 м³/сут. Терминальный source-bound receipt v2.1
зафиксировал no-op `110,782383361` и alternative 140 `110,776225880` млн руб.
No-op лучше на `0,006157480` млн руб. Эти значения сопоставимы только между
собой на одномесячном интервале и не доказывают полный горизонт; рекомендация
остаётся baseline/no-op. Receipt не является сертификацией организаторов.

### Роли многоагентной системы

Роли являются узлами одного устойчивого workflow, а не десятками автономных
чатов.

| Роль | Ответственность | Что ей запрещено |
|---|---|---|
| Координатор | проверяет цель, состояние и готовность evidence | назначать режимы напрямую |
| Аналитик пласта | интерпретирует только переданные факты и ограничения | придумывать дебиты и состояние |
| Планировщик | предлагает структурированный вариант и вызывает валидатор controls | писать deck или запускать shell |
| Критик | блокирует план без достаточного OPM/CHDD evidence | смягчать hard constraints |

Это ровно четыре роли из текущего `ROLE_ORDER`; шесть блоковых агентов,
отдельный нарратор и агент на каждую скважину относятся только к возможной
последующей декомпозиции и в КТ2 не заявляются.

Не нужен агент на каждую скважину: скважины физически связаны, а такая
декомпозиция создаёт конфликт целей и не даёт корректного разложения вклада.

### Параметризация действий

Сначала оптимизируется низкоразмерное намерение:

- бюджет закачки по шести блокам;
- доли 16 нагнетательных внутри блока;
- групповые множители отбора;
- небольшой набор кандидатов на открытие/закрытие;
- редкие переводы фонда;
- горизонт удержания режима и гистерезис.

Затем детерминированный проектор разворачивает намерение до скважинных
управлений. Это уменьшает размерность и не позволяет LLM случайно нарушить
баланс.

Рекомендуемые правила:

- горизонт MPC 3–6 месяцев;
- фиксация только первого месяца;
- stop/start не чаще минимального времени удержания;
- перевод фонда — отдельное редкое дискретное решение;
- плавные изменения непрерывных режимов;
- общий объём закачки сохраняется, если тестовый кейс не разрешает иное.

### Целевой численный поиск после КТ2

Желаемый каскад для дорогой полной ГДМ:

1. Sobol-набор допустимых начальных кандидатов.
2. CVXPY/SciPy-проекция линейных и выпуклых ограничений.
3. Prescreen существующими CRM, CRMP, двухфазной CRM и моделью Джентила.
4. Optuna GPSampler как простой основной байесовский поиск.
5. BoTorch/TuRBO для локального дорогого поиска, если Optuna достиг потолка.
6. Полная ГДМ для финалистов.
7. Локальная доводка SLSQP около лучшего подтверждённого решения.

Существующий [FieldOpt](https://github.com/PetroleumCyberneticsGroup/FieldOpt)
стоит проверить коротким spike: он уже решает задачи управления
месторождением и параллелит целевую функцию. Но GPL-3.0, сборка и адаптация
deck могут оказаться дороже, чем прямой слой Optuna. Поэтому FieldOpt —
кандидат на повторное использование, а не обязательная зависимость.

RL/PPO/MAPPO не должны быть основой Track 1: данных мало, симулятор дорог,
награду легко эксплуатировать, а воспроизводимость хуже. RL допустим только как
последующее сравнительное расширение.

### Контракт полной ГДМ

SimulatorBackend должен поддерживать:

- validate_case;
- run_history_match/replay;
- run_from_restart;
- extract_state;
- extract_chdd_frame;
- get_failure;
- get_provenance.

Основная открытая реализация — [OPM Flow](https://github.com/OPM/opm-simulators),
полностью неявный black-oil симулятор с Eclipse-совместимыми форматами. На дату
документа актуальная стабильная ветка — [2026.04](https://github.com/OPM/opm-simulators/releases).

Model Y нативно ориентирован на tNavigator, поэтому паритет базового replay в
OPM был обязательным шлюзом:

- deck проходит без молчаливого удаления ключевых конструкций;
- даты, статусы и фонд совпадают;
- дебиты и накопленные показатели находятся в согласованном допуске;
- 14 полей CHDD извлекаются одинаково;
- baseline ЧДД воспроизводим.

Шлюз закрыт для КТ2: OPM Flow 2026.04 завершил baseline, все 18 годовых
массовых векторов прошли допуски, а ЧДД попал внутрь опубликованного
межсимуляторного диапазона. Это подтверждает пригодность текущего OPM adapter
для демонстрации. Оно не гарантирует паритет неизвестного финального кейса:
при изменении deck gate выполняется заново.

### Месячный цикл принятия решения — целевой после КТ2

Для месяца t целевой цикл таков:

1. загрузить restart полной ГДМ;
2. построить ReservoirState и активные ограничения;
3. получить от агентов не более нескольких ControlIntent;
4. развернуть их в допустимые ControlAction;
5. добавить кандидатов численного оптимизатора;
6. отсечь слабые варианты дешёвыми моделями;
7. запустить полную ГДМ параллельно для оставшихся;
8. получить 14 полей и точный CHDD;
9. проверить ограничения, устойчивость и чувствительность;
10. выбрать действие только среди прошедших;
11. создать контрфактуал «оставить baseline» и «убрать главное действие»;
12. зафиксировать первый месяц;
13. сохранить restart, trace и decision card;
14. перейти к t+1.

При падении всех кандидатов применяется заранее валидированный baseline/no-op,
а не выдуманное действие.

### Целевая функция

Основная цель — официальный ЧДД. Для нескольких сценариев неопределённости:

\[
J(x)=\operatorname{CVaR}_{0.1}
\left(\operatorname{CHDD}_{official}(GDM(x))\right)
-\lambda_s P_{soft}(x).
\]

Hard constraints в P_soft не входят: они блокируют x до ранжирования.

Неопределённость Track 1 оценивается не «доверительным интервалом LLM», а
повторным расчётом ограниченного набора сценариев: чувствительность к
ограничениям, небольшим изменениям управления и допустимым вариантам
исходного состояния.

### Что повторно использовать из TimesOil

- data.py/wells.py как проверенный адаптер истории Model Y;
- CRM, CRM2P, CRMP, адресную закачку и Джентил как каскад физического
  предварительного отсева;
- LightGBM, Chronos-2, TiRex-2 и TiDE как сравнительные прогнозные голоса;
- run_scenario_augmentation как проверку устойчивости кандидата на нескольких
  уже имеющихся сценариях Model Y;
- WAPE, rolling backtest, ансамбли и crepes-интервалы как диагностику риска;
- optimize_injection как исходную реализацию локальной SLSQP-доводки, расширив
  её с постоянных множителей закачки до типизированного ControlAction;
- автономное ядро CHDD, но только через новый fail-closed adapter с явной датой;
- подготовку графиков и отчётность после переноса в неизменяемый run directory.

Текущий стек 3,744%/3,206% является оценочным out-of-fold результатом: у него
нет воспроизводимого producer для stack_final, fit-on-all и forward-сериализации.
Поэтому ни он, ни отдельные прогнозные модели не заменяют GdmWorldModel и не
сертифицируют конкурсный план.

## Track 2 — архитектура суррогатного цифрового двойника

### Основное решение

Реализованный Track 2 КТ2 — гибридная модель уровня скважин:

~~~text
проверенные полные OPM-траектории Model Z
  → physical baseline: CRM/material balance
  → residual features: state + control + target + status
  → bootstrap ensemble LightGBM, по модели на каждый из 3 выходов
  → physical projection
  → recursive six-month rollout
  → ensemble disagreement + feature-range OOD
~~~

Физический переход оценивает затухание жидкости, отклик на закачку, удержание
нефтяной доли и баланс/релаксацию давления. LightGBM с
`objective=regression_l1` учит только остаток следующего состояния. Пять
участников ансамбля получают bootstrap-выборки целых сценариев, а не случайных
строк. Масштаб остатка выбирается по out-of-bag ошибке. Такой состав прямо
следует из [surrogate.py](../../src/timesoil/aios/surrogate.py); графовых слоёв,
TCN и GRU в текущей модели нет.

Типизированный `StatefulSurrogate` поддерживает `step`, рекурсивный `rollout` и
batch `predict`; модель сохраняется вместе со схемой, baseline, booster-файлами,
порогами OOD, seed и хэшами сценариев.

### Целевая архитектура после КТ2: граф/нейрооператор только как benchmark

512 сценариев × 225 месяцев × 547 638 ячеек × два FP32-поля — около 500 ГБ
ещё до статических каналов, градиентов и промежуточных активаций. Полный
нейрооператор технически возможен, но подготовка данных и rollout становятся
главным риском хакатона.

[NVIDIA PhysicsNeMo](https://docs.nvidia.com/physicsnemo/latest/) предоставляет
готовые Apache-2.0 реализации MeshGraphNet, FNO и SciML-компоненты;
[NeuralOperator](https://github.com/neuraloperator/neuraloperator) содержит
FNO, GINO, LocalFNO и UQNO. Их следует оставить как последующее исследование:

- POD/autoencoder сжатие grid state;
- FNO/GINO на сжатом поле;
- teacher для well-graph surrogate;
- резерв, если модель уровня скважин достигла потолка.

Если текущий ансамбль упрётся в измеримый потолок на существенно большем
scenario-level test, можно сравнить PyTorch Geometric/PhysicsNeMo. До такого
эксперимента эти зависимости не входят в поставку.

### Генерация обучающих данных

OPM работает на CPU; A100 используются для обучения, а не генерации deck-run.
Фактический минимальный пакет КТ2 содержит четыре сценария: identity-baseline с
побайтно исходным schedule include и три детерминированных возмущения с seed
20260831 и пределом 15%. В каждом 38 213 действий, 371 месяц и 103 скважины.
Суммарная месячная закачка, роль, статус, тип target и вторичные позиционные
WCON-ограничения, включая BHP, сохраняются; LRAT не превышает 500. Повторная
генерация byte-identical подтверждена receipt
`f8284da948312446318e14acaf768bd2f06bacb61dec7f1fc667b7400b4273d9`; runner
принимает индекс только с внешне закреплённым SHA-256
`71edcb70cf4e04871f81e6d6ed4842f8cc91d542731024269060a1c8f5cfaf54` и сверяет
identity baseline с эталонным CHDD
`446c24eaa063710422835a745be157abdce66d602c75f33de50a8e75881d3884` до запуска
perturbations.

Все четыре OPM-траектории завершены. Receipt
[`track2_scenario_batch_completion_a100_v1.json`](./evidence/track2_scenario_batch_completion_a100_v1.json)
имеет SHA-256
`d50386ca122c5e3608b14157661ff0974c9329f89072e7b46cbfc3b3d0f797b6`;
собранный dataset —
`1253a351c8ea58dbd7e618cd50b9817f6d6b646962d2052744d4efb21a778cc0`.

Целевые семейства сценариев после КТ2:

1. baseline replay;
2. малые безопасные возмущения;
3. скважинные impulse-тесты;
4. Sobol по группам управления;
5. stop/start и переводы;
6. ограничения давления и закачки;
7. граничные допустимые режимы;
8. локальные возмущения лучших найденных планов.

Для плана экспериментов достаточно
[scipy.stats.qmc.Sobol](https://docs.scipy.org/doc/scipy/reference/stats.qmc.html).
Параллельные OPM-запуски выполняются отдельными процессами с изолированными
рабочими каталогами.

Целевая acquisition-функция active learning:

\[
a(x)=Disagreement(x)\cdot
Sensitivity_{CHDD}(x)\cdot
Diversity(x).
\]

То есть новый дорогой прогон выбирается там, где неопределённость способна
изменить экономическое решение, а не просто там, где велика ошибка модели.

### Выходы и физические инварианты

Текущая модель прогнозирует следующее месячное состояние каждой скважины:
нефть, жидкость и давление. Управление задаётся тройкой control value, target
code и status; закачка и статус не прогнозируются сетью.

Детерминированная проекция обеспечивает:

- нефть ≥ 0;
- жидкость ≥ нефть;
- закрытая скважина не создаёт поток;
- давление ≥ 0.

WLPR ≤ 500, сохранение месячной суммарной закачки и корректность target/status
обеспечиваются генератором сценариев и валидатором управления. Накопленные
поля и Diff формируются детерминированно только перед официальным CHDD.

### Обучение и контроль качества

Текущая целевая функция каждого booster — L1-ошибка остатка следующего
состояния. Разделение выполняется по целым OPM-сценариям, не по случайным
строкам. Отдельно считаются шестимесячные recursive-rollout метрики:
WAPE нефти/жидкости, RMSE давления, средняя ошибка окон, покрытие ансамбля и
доля OOD-шагов. Сравнение с чистым physical baseline входит в training report.

Training v3 завершён на 183 train- и 61 test-rollout. Train WAPE
нефти/жидкости — `7,1949 %`/`4,5042 %`, RMSE давления — `8,728 bar`, OOD —
`0,7286 %`, nominal 90%-coverage — `43,71 %`. Test: `7,7940 %`/`5,1943 %`,
`8,808 bar`, `0,5464 %` и `40,50 %` соответственно. Неопределённость —
ensemble std, не конформно откалиброванный интервал; низкое покрытие нельзя
выдавать за 90%-гарантию. Receipt
[`model_z_track2_training_terminal_a100_v3.json`](./evidence/model_z_track2_training_terminal_a100_v3.json)
имеет SHA-256
`511e1950d43244ab9cd7ca034a26cd811e7532df155fe259555728a53c10036a`;
15 из 15 booster-хэшей совпали с первоначальным артефактом.

OOD gate учитывает три измеримых сигнала:

- выход state/control residual features за диапазон обучения;
- нормированное disagreement ансамбля;
- долю слишком большой физической проекции.

Высокий OOD означает обязательный OPM-прогон или откат к ближайшему
подтверждённому плану.

### Model Z overlay

Оригинальный архив и deck остаются неизменными; runner работает только с
изолированным snapshot. Для сценария `baseline` документированный schedule
include копируется побайтно, его SHA равен исходному, а полученный 14-польный
CHDD обязан совпасть с authenticated baseline SHA до запуска perturbations.

Для трёх perturbations overlay вставляет WCON-записи в существующие месячные
границы подготовленной копии. Он меняет только status, control mode и основную
уставку, а остальные позиционные ограничения исходной effective WCON-записи,
включая BHP `50` у добывающих и `300` у нагнетательных, переносит без потери.
Однострочный поддерживаемый синтаксис разбирается fail-closed; при неизвестной
форме прогон запрещён. Полный канонический `wells_schedule.inc` сохраняется как
отдельный хэшированный артефакт, но simulator получает проверенную копию
исходного include с наложением. Индекс bundle также поступает в runner только
с заранее подтверждённым SHA-256.

Независимый SUMMARY overlay добавляет требуемые векторы и сохраняет исходную
точку INCLUDE и provenance команды извлечения.

Текущий extractor читает необходимые SUMMARY-векторы и deck/PVT-метаданные;
RESTART, INIT, RFT и GRID не входят в доказанный Track 2 pipeline КТ2.
Поскольку OPM и ResData имеют GPL-3.0, условия распространения образа нужно
проверить до передачи, а не считать API-границу автоматическим исключением.

## LLM-провайдер для обоих треков

Архитектурное решение от 31.08.2026: единственная языковая модель AIOS —
**Qwen3.6-35B-A3B через Tatneft LiteLLM**.

~~~text
LLM_BASE_URL=https://litellm.tatneft.guru/v1
LLM_MODEL=qwen3.6-35b-a3b
LLM_PROVIDER_CLASS=approved_external
LLM_PROVIDER_WIRE_MODE=chat_template
~~~

Локальные Qwen, vLLM и другие LLM не используются даже как резерв. При
недоступности Tatneft LiteLLM агентный контур завершается с явной ошибкой и не
формирует управляющее расписание.

Контракт первоначально сверялся с рабочим контуром nsi_analytics. В TimesOil
теперь реализован собственный минимальный `TatneftLLMClient` с жёстко
зафиксированными endpoint и model allowlist:

- endpoint и POST /v1/chat/completions доступны с A100;
- reasoning возвращается в reasoning_content;
- chat_template_kwargs с enable_thinking=false отключает рассуждение;
- response_format=json_schema совместим с отключённым thinking;
- модель принимает большой контекст;
- прямой доступ из локального WSL не гарантирован, поэтому live-проверки и
  демонстрация выполняются на A100.

Терминальный receipt
[`qwen36_agent_tool_registry_a100_v3.json`](./evidence/qwen36_agent_tool_registry_a100_v3.json)
(SHA-256
`6098179b0f21362a8cde72c58a5156616f5986729c1fffea978272b53ed8b1c5`)
подтверждает один host-side A100 live-workflow через внешний Tatneft LiteLLM:
`complete=true`, exit 0, 8/8 provider responses, четыре роли и четыре реальные
allow-listed read-tool calls без retry. Точная модель — `qwen3.6-35b-a3b`,
локальная модель и fallback не использовались. Секрет, reasoning и raw content
не копировались, не печатались и не сохранялись.

Role approvals равны `[true, true, true, false]`; `critic_approved=false` —
это явный отказ критика, а не положительная сертификация. Agent-tool context
охватывал точный ограниченный срез из 412 действий за январь–апрель, а не все
618 действий. Полное расписание из 618 действий отдельно прошло OPM replay и
официальный расчёт ЧДД `11918,789227262983` млн руб.; Qwen сам не запускал OPM
или ЧДД и остаётся рекомендательным слоем. Неизменяемая предыдущая попытка
[`qwen36_agent_terminal_failure_a100_v2.json`](./evidence/qwen36_agent_terminal_failure_a100_v2.json)
(SHA-256
`e3a8fe69cc2764972e3679edb953e6f599c87875ef39718923f5a8bdb6547ecb`)
сохраняет таймаут до заголовков ответа и нулевое число ответов/ролей/tools.
Terminal v3 не является provider attestation, не доказывает Compose→Qwen,
не калибрует uncertainty conformally и не даёт organizer certification.

Секрет передаётся только через защищённое runtime-окружение. API-ключ запрещено
сохранять в Git, env.example, Docker image, командах, логах и артефактах.

Перед допуском AIOS необходим короткий gate:

- корректный вызов allow-listed инструментов;
- валидный Pydantic JSON;
- понимание единиц и ограничений;
- устойчивость к prompt injection из deck и отчётов;
- повторяемость при temperature 0;
- контролируемое поведение при 401/429/5xx и таймауте.

## Оркестрация агентов

Текущая реализация не использует внешний графовый оркестратор. Собственный
`AgentWorkflow` выполняет фиксированный переход:

~~~text
coordinator → reservoir_analyst → planner → critic
~~~

Контекст нормализуется в bounded JSON; переход к следующей роли возможен только
после структурированного ответа ожидаемой роли. `ToolRegistry` проверяет имя,
allowlist роли, JSON Schema, размер аргументов/результата и запрещает любой
не зарегистрированный инструмент. Инструменты только читают переданное
состояние/evidence и валидируют candidate controls; они не запускают shell,
OPM или CHDD. Численный workflow остаётся отдельным детерминированным контуром.

Долговременное checkpoint/resume — целевая функция после КТ2. Сейчас
идемпотентность численных запусков обеспечивается content hashes, уникальными
run directories и запретом перезаписи, а не состоянием стороннего workflow.

## API-контур

Внешний фасад — FastAPI. Реализованные маршруты КТ2:

- `GET /` — встроенная операторская HTML-страница;
- `GET /health`;
- `GET /v1/capabilities` с честными `certified=false`;
- `POST /v1/experiments/agents` — четыре роли Qwen3.6;
- `POST /v1/economics/chdd` — официальный CHDD.

Jobs, polling/SSE, загрузка кейсов, GDM/surrogate endpoints и API-выгрузка
evidence относятся к целевой архитектуре после КТ2. Численные сценарии КТ2
запускаются воспроизводимыми CLI, а не несуществующими HTTP-маршрутами.

LLM API не публикуется наружу напрямую. FastAPI выдаёт ему только allow-listed
инструменты с короткими схемами и ограниченными таймаутами.

## Хранение и воспроизводимость

Для хакатона не нужны Kafka, Kubernetes, Celery и распределённая база.

- CSV/JSON — канонические траектории, метрики и manifests КТ2;
- файловые run directories — deck snapshots, overlay, schedule, SUMMARY,
  экономика и evidence;
- SHA-256 — связь входов, исходников и результатов;
- LightGBM native files + JSON schema/metadata — сериализация суррогата.

Parquet/DuckDB, SQLite-очередь, MLflow и OpenTelemetry — возможное развитие
после КТ2, но текущая поставка от них не зависит.

Каждый run directory:

~~~text
run/
  manifest.json
  case/
  constraints/
  intents/
  controls/
  simulations/
  trajectories/
  economics/
  schedule/
  evidence/
  logs/
~~~

Данные не перезаписываются. Новый эксперимент создаёт новый run_id.

## Наблюдаемость и интерпретируемость

Текущая наблюдаемость основана на структурированных agent decisions,
tool evidence, OPM/CHDD manifests и SHA-256 receipts. Скрытые рассуждения Qwen
не сохраняются. MLflow/OpenTelemetry не входят в доказанную поставку КТ2 и
могут быть добавлены после появления нескольких параллельных run workflows.

Для каждого принятого действия создаётся decision card:

- состояние до действия;
- изменение режимов;
- ожидаемый эффект по нефти, жидкости, закачке и давлению;
- точный/прогнозный CHDD и его статус;
- активные ограничения;
- uncertainty и OOD;
- результат полной ГДМ;
- контрфактуал без действия;
- ближайшие отвергнутые альтернативы;
- run_id и хэши артефактов.

Интерпретируемость строится на вычислимых фактах. Attention map и скрытая
цепочка рассуждений LLM не считаются доказательством.

## Пользовательский интерфейс

Реализованный UI — встроенная доступная HTML/JavaScript-страница FastAPI без
отдельного frontend runtime. Она показывает health/capabilities, подчёркивает
разницу между `available` и `certified`, принимает bounded JSON-контекст и
показывает структурированный результат четырёх ролей.

Целевая панель после КТ2 может добавить:

1. загрузка и валидация тестового кейса;
2. статус симулятора, LLM и CHDD;
3. карта блоков/скважин и граф связности;
4. baseline против optimized;
5. нефть, жидкость, закачка, давление;
6. waterfall ЧДД;
7. ограничения и нарушения;
8. uncertainty/OOD;
9. журнал агентных действий;
10. decision cards;
11. финальный replay;
12. выгрузка wells_schedule.inc, manifest и отчёта.

UI не редактирует расписание после запуска. Кнопка выгрузки активируется только
после зелёного parser round-trip, GDM replay и CHDD.

## Развёртывание на a100

Текущий Docker Compose содержит один минимальный сервис `api`; отдельные
worker/ui/mlflow/opm-runner/trainer не создаются до появления реальной
потребности. API запускается непривилегированным UID 10001, с read-only rootfs,
`cap_drop: ALL`, `no-new-privileges`, tmpfs и secret mount. Порт публикуется
только на `127.0.0.1`.

LLM не входит в Compose: сервис `api` обращается к Tatneft LiteLLM через
защищённые переменные окружения.

Минимальный API image — control plane, а не самодостаточный численный пакет:
в него входят API-исходники и CHDD, но не OPM, Track 2 training/search CLI,
веса модели и крупные внешние артефакты. Доказанные A100-артефакты остаются
внешними и подключаются явно.

Поставка поэтому состоит из двух явных частей: terminal API/control-plane
image и отдельный host-side numerical bundle с OPM, Model Z artifacts,
`track2_model_z_v3` и evidence receipts. Успешный health API не заменяет
численный комплект и его SHA-256 lineage.

Terminal receipt
[`docker_a100_v5.json`](./evidence/docker_a100_v5.json), SHA-256
`c7a48d202cd337f3d0915aac47688834d8a5ff6647b1aa6911535f633f00cf12`,
подтверждает fresh-context build и runtime: UID 10001, `CapEff=0`,
no-new-privileges, read-only rootfs, loopback HTTP и Compose-run doctor PASS.
Ключ материализуется из защищённого источника только в RAM-файл
`/dev/shm/timesoil-qwen-api-key` с owner `10001:10001`, mode `0400`; наружу
экспортируется только `QWEN_API_KEY_FILE`, Compose монтирует file secret.
Пустой или недоступный secret fail-closed; контейнер, сеть, volume и RAM-файл
удалены после проверки. Qwen workflow/connectivity receipt v5 не проверял.

OPM запускается как CPU subprocess в изолированном рабочем каталоге. Не нужно
контейнеризировать каждый месячный шаг отдельно, если один неизменяемый
opm-runner уже обеспечивает изоляцию и хэши.

### GPU-профиль

Ни одна карта не считается свободной заранее; перед каждым запуском обязателен
nvidia-smi.

При шести действительно свободных A100:

- GPU 0–5 — независимые члены ансамбля или подбор параметров Track 2;
- после обучения один GPU — surrogate inference, остальные освобождаются.

Из-за отсутствия NVLink предпочтительны независимые задачи 1-на-GPU. Tensor
parallel для LLM не нужен: Qwen3.6 обслуживается Tatneft LiteLLM вне
вычислительного контура TimesOil.

## Schedule compiler

Канонический `ScheduleCompiler` — критический детерминированный компонент:

1. принимает только типизированные `ControlAction`;
2. проверяет скважины и их роль на дату;
3. проверяет допустимые control target, status, диапазон дат и LRAT;
4. сортирует даты;
5. строит поддерживаемое подмножество DATES/WCONPROD/WCONINJE;
6. не меняет исходный deck;
7. повторно читает результат собственным строгим parser;
8. сравнивает round-trip с исходными действиями;
9. блокирует артефакт при расхождении;
10. сохраняет SHA-256.

Track 2 добавляет поверх него lossless overlay исходного schedule include.
Identity-baseline не получает WCON-вставок и сохраняется побайтно; для
perturbations меняется только основная уставка в последней effective
WCONPROD/WCONINJE-записи, а остальные позиционные поля, включая BHP, переносятся
без потери. Runner отдельно проверяет внешний SHA индекса bundle и эталонный SHA
CHDD identity-baseline; self-authenticated manifest для этих gates недостаточен.

Для выданных Model Y/Model Z INCLUDE point и поддерживаемый синтаксис уже
зафиксированы и проверены. Расширение на бурение, смену роли и новые keywords
возможно только после получения соответствующего конкурсного контракта.

## Защитный контур

Реализованные gates КТ2:

1. Schema gate.
2. Unit gate.
3. Constraint gate.
4. Simulator success gate.
5. Trajectory invariant gate.
6. CHDD completeness gate.
7. Surrogate UQ/OOD gate для Track 2.
8. Schedule parser round-trip.
9. Full replay gate для подтверждённого кандидата.
10. Artifact hashes/manifest gate.
11. Authenticated scenario-index gate.
12. Byte-identity и golden CHDD gate для Model Z baseline до perturbations.

Повторный чистый replay полного финального решения обоих треков остаётся
критерием релиза после КТ2, а не уже закрытым фактом.

При любом красном gate результат не маскируется LLM-объяснением.

4. Qwen3.6-only клиент, собственный четырёхролевой workflow, allow-listed
   инструменты, API и встроенная панель.
5. Model Z scenario bundle: byte-identity baseline, lossless WCON secondary
   constraints, authenticated index/CHDD gates и код суррогата
   CRM/material-balance + LightGBM residual ensemble.
6. Четыре Model Z OPM-траектории, training v3 и search v3: 32/32 кандидата

### Незакрытая внешняя граница

1. Организаторская сертификация обоих треков отсутствует. Qwen terminal v3 —
   рекомендательное evidence, а не provider attestation или сертификация
   расписания.

### Целевая архитектура после КТ2

1. Бинарный restart и доказанный многомесячный MPC Track 1.
2. Больше OPM-сценариев, active learning и отдельный optimizer-distribution
   test Track 2.
3. Расширение пространства действий после получения финального контракта.
4. Байесовский/эволюционный поиск, робастная цель и clean-room replay.
5. Долговременная очередь/registry и расширенная визуализация.
6. FNO/GINO или well-graph только как benchmark после измеренного потолка

## Критерии финальной готовности Track 1 после КТ2

- baseline replay воспроизводится дважды из чистого окружения;
- каждый принятый месячный шаг имеет успешный GDM result;
- ни одного отрицательного Diff;
- WLPR не превышает 500;
- start date CHDD явно равна 2014-01-01;
- schedule проходит parser round-trip;
- финальный replay использует только сгенерированный wells_schedule.inc;
- заявленный CHDD равен пересчитанному в согласованном допуске;
- нет ручной правки после старта;
- каждый вывод LLM ссылается на run_id или численный факт;
- пакет содержит код, lock, конфиг, веса/инструкцию получения, manifest,
  документацию и команду одного запуска.

## Критерии полной organizer-ready готовности Track 2

- **PASS self-replay:** OPM baseline Model Z воспроизводим;
- **PASS:** SUMMARY overlay выдаёт все 14 полей;
- **PASS:** start date CHDD явно равна 2007-01-01;
- **PASS:** train/test разделены по целым сценариям;
- **не доказано:** surrogate не продемонстрировал улучшение baseline; выбран

- **не доказано:** ensemble std не conformal, nominal 90%-coverage только

- **частично:** search принял 32/32 кандидата, но обучающих OPM-траекторий

- **не выполнено:** `organizer_certified=false` до внешней проверки.

| Риск | Основной ответ | Запасной режим |
|---|---|---|
| Финальный Model Y отличается от проверенного deck | повторить OPM/ЧДД parity gate | не переносить baseline-допуск автоматически |
| Неясен schedule contract | запрос организаторам | минимальный baseline include, без расширений |
| Мало GDM-бюджета | CRM prescreen + GPSampler | локальный поиск вокруг baseline |

| LLM нарушает схему | Pydantic validation и ограниченный повтор | отклонить действие |
| Все GPU заняты | CPU OPM, отложить training | последовательный один-GPU режим |
| Track 2 мало данных | текущий CRM + LightGBM residual ensemble | уменьшить пространство действий и не заявлять обобщение |
| LightGBM residual не лучше physical baseline | оставить physical baseline | расширить DoE, затем benchmark сложной модели |
| Surrogate OOD | новый OPM run | ближайший подтверждённый план |
| Optimizer exploit CHDD | invariant gate | fail closed |
| Ошибка OPM/CHDD | аварийное завершение | запрещена подстановка прогноза |

## Что делает решение действительно отличимым

1. **Simulator-certified actions:** LLM предлагает, но только полная ГДМ
   создаёт принятое состояние Track 1.
2. **Physical-residual surrogate:** Track 2 не переучивает доступную физику, а
   добавляет к ней компактный ансамбль LightGBM-остатков.
3. **Scenario-level provenance:** суррогат обучается только на целых проверенных
   OPM-траекториях с хэшами, без перемешивания строк между split.
4. **Exact economics at certification:** официальный CHDD используется после
   полной ГДМ; Track 2 proxy явно не называется ЧДД.
5. **Fail-closed uncertainty:** OOD — блокирующий gate.
6. **Grounded explanations:** Qwen получает только bounded state/constraints/
   evidence; численные утверждения не извлекаются из скрытого reasoning.
7. **Self-checking schedule:** ControlPlan и распарсенный include должны
   совпасть.
8. **Swappable world model:** общие contracts обслуживают оба трека.
9. **Immutable evidence chain:** доказанные итоги ведут к deck, симуляции,
   экономике, seed и SHA-256; Track 2 self-replay chain завершена audit v3.

## Ограничения этой архитектуры

- Финальный тестовый кейс и расширенный schedule contract не предоставлены;
  доказан только синтаксис выданных Model Y/Model Z и поддерживаемое подмножество
  DATES/WCONPROD/WCONINJE.
- OPM запускается pinned Docker-образом на A100 CPU; локальная установка
  симулятора не требуется. tNavigator adapter не реализован.
- Track 1 использует full replay и не извлекает бинарный restart. Доказан один
  месяц, не автономный многомесячный цикл.
- Результат стека 3,744%/3,206% подтверждён как оценочная метрика, но текущий
  репозиторий не воспроизводит из кода stack_final и не применяет этот стек к
  forward-прогнозу.
- Model Z training v3 завершён: test WAPE нефти/жидкости
  `7,7940 %`/`5,1943 %`, RMSE давления `8,808 bar`, OOD `0,5464 %`.
  Nominal 90%-coverage равен только `40,50 %`; ensemble std не conformal.
- Финальный Track 2 OPM→CHDD self-replay завершён с ЧДД
  `11918,789227262983` млн руб.; выбран baseline, поэтому улучшение не
  заявляется, `organizer_certified=false`.
- Четыре Model Z траектории достаточны для демонстрации pipeline, но слишком
  малы для production-утверждений и сложной модели.
- Search v3 оставил baseline с proxy `127494,1351`; proxy не ЧДД. Последующий
  OPM replay подтверждает выбранное расписание, но не делает proxy официальной
  экономической целью.
- API пока не запускает длительные OPM/training jobs; операционные численные
  прогоны выполняются CLI. Минимальный API image не содержит OPM, Track 2 CLI,
  веса модели или крупные A100-артефакты.
- Docker v5 подтверждает финальный API image и runtime/security, но не содержит
  OPM/Model Z и не вызывал Qwen workflow.
- Агентный слой зависит от сетевой доступности Tatneft LiteLLM с A100 и
  корректного runtime-секрета; локального LLM-резерва по решению команды нет.
  Terminal v3 — host-side evidence, не provider attestation и не Compose-path.
  Он проверил только точный 412-action срез января–апреля; полное расписание из
  618 действий валидировано отдельно OPM replay. `critic_approved=false`, Qwen
  не выполнял OPM/ЧДД, uncertainty не conformally calibrated, а
  `organizer_certified=false`.
- Юридические обязанности GPL и неуказанная лицензия CHDD требуют проверки
  перед передачей контейнера.
