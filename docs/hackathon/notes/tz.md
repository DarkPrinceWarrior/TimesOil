# Техническое задание хакатона AIOS

Справочная выжимка по официальному ТЗ хакатона «Мультиагентные системы ИИ ОС в НГК». Подробности по трекам — в [tracks.md](tracks.md); порядок сдачи, допуск к проверке и уточнения из канала — в [submission.md](submission.md).

## Назначение ТЗ

Участникам предлагается разработать программное решение для **оптимального управления разработкой нефтяного месторождения** на основе предоставленной **гидродинамической модели**. Решение формирует управляющие последовательности работы скважин и максимизирует экономический эффект, выраженный показателем **чистого дисконтированного дохода** (NPV, далее — **ЧДД**).

Цели хакатона: выявить эффективные подходы к управлению разработкой с помощью **мультиагентной системы**; продемонстрировать прирост ЧДД по сравнению с базовым управлением; проверить готовность решений к масштабированию на реальные данные.

## Одно ТЗ — два трека

Хакатон проводится в формате **единого технического задания для двух треков**. Участник выбирает **один** трек по своей компетенции и подходу.

**Трек 1 — мультиагентная система на гидродинамической модели.** Многоагентный подход формирует и корректирует управляющие воздействия на основе расчётов по полной гидродинамической модели на каждом шаге.

**Трек 2 — масштабируемая мультиагентная система с суррогатными моделями.** Мультиагентная система использует обучаемые (нейросетевые, суррогатные) модели для ускоренного прогнозирования поведения месторождения; полная гидродинамическая модель остаётся эталоном для проверки результата.

Общий итог обоих треков: файл **`wells_schedule.inc`** с управляющим графиком работы скважин, совместимый с моделью организаторов, и **расчётное значение ЧДД** по сформированной последовательности управления.

Сравнение треков, моделей и дополнительных требований — в [tracks.md](tracks.md).

## Цикл управления

Решение работает в цикле:

**оценка состояния → выработка решения → передача управляющего воздействия → повторная оценка**

На каждом расчётном шаге система анализирует текущее состояние объекта разработки, формирует рекомендации по управлению скважинами (открытие и закрытие, изменение режимов, иные допустимые воздействия по постановке), учитывает технологические и физические ограничения модели и регламента и стремится максимизировать ЧДД.

## Обязательные свойства решения

Независимо от трека, по ТЗ (§ 3.1) решение должно включать:

1. **Языковая модель в ядре.** Слой агентов с **языковой (мультимодальной) моделью** в ядре — обязательное требование, а не опция.
2. **Слой интерпретируемости.** Система должна давать возможность понять логику решений и разобрать результат работы мультиагентной системы.
3. **Простой графический интерфейс.** Интерфейс, достаточный для взаимодействия с мультиагентной системой и интерпретации результатов.

Дополнительно для обоих треков (§ 1.3, § 3.1):

- приём и обработка входных данных организаторов;
- генерация корректного **`wells_schedule.inc`**;
- расчёт и передача значения ЧДД;
- запуск в стандартной вычислительной среде;
- воспроизводимость на тестовом кейсе;
- соответствие ограничениям и условиям организаторов.

## Входные и выходные данные

### Вход

Организаторы предоставляют (§ 5.1):

- исходную гидродинамическую модель месторождения;
- **тестовый кейс** для первичного запуска (на этапе валидации);
- информацию, необходимую для формирования **`wells_schedule.inc`**;
- регламент хакатона и календарный план;
- иные материалы, прямо указанные в сопроводительной документации.

Состав и формат входных данных должны быть **достаточны для запуска без самостоятельного формирования недостающих исходных файлов** (§ 3.3.1).

### Выход

Решение формирует (§ 3.3.2):

- **`wells_schedule.inc`** — управляющие последовательности, совместимые с расчётной моделью организаторов и пригодные для дальнейшего расчёта **без ручного редактирования**;
- **значение ЧДД**, полученное в результате запуска;
- при необходимости — служебные файлы для воспроизводимости расчёта и проверки.

## Пакет сдачи

Для **допуска к автоматической валидации** участники обязаны предоставить (§ 3.4):

| Компонент | Обязательность по ТЗ |
|-----------|----------------------|
| Исходные коды | да |
| Документация к решению | да |
| Инструкция по развёртыванию и запуску | да |
| Файл конфигурации для воспроизведения результата | да |
| Docker-образ или материалы для однозначной сборки | **при использовании контейнеризации** |
| Результаты запуска на тестовом кейсе: **`wells_schedule.inc`** и заявленное значение ЧДД | да |

**Расхождение с официальным постом канала.** В посте Docker указан как «если используете»; в ТЗ (§ 3.4) образ или материалы для сборки требуются **только при контейнеризации**. Остальные пункты пакета обязательны всегда.

Ожидаемый итог работы (§ 1.4, § 8.1): работоспособное решение, **`wells_schedule.inc`**, значение ЧДД на тестовом кейсе, комплект исходных материалов для проверки и воспроизведения.

Порядок передачи материалов и дополнительные уточнения из канала — в [submission.md](submission.md).

## Воспроизводимость

Решение должно давать **сопоставимый результат** при повторном запуске в идентичной среде с теми же исходными данными (§ 3.5).

**Не допускается:**

- скрытые зависимости;
- неописанные внешние ресурсы;
- неконтролируемые параметры, мешающие проверке организаторами.

Решение должно быть пригодно для **автоматической или полуавтоматической проверки** (§ 3.1) и запускаться в стандартной вычислительной среде без сложной ручной настройки инфраструктуры (§ 3.6).

## Два этапа проверки

Проверка проводится в **два этапа** (§ 4.1): первичный отбор и финальная проверка.

### Этап 1 — первичный отбор (автоматическая валидация)

**Допуск** — только при представлении исходных кодов, документации, материалов для воспроизведения и результатов запуска на тестовом кейсе (§ 4.2). Без полного комплекта валидация не проводится.

**Процедура** (§ 4.3): участник запускает систему на тестовом кейсе, формирует **`wells_schedule.inc`**, вычисляет ЧДД и передаёт результаты в формате организаторов.

**Отбор:** команды ранжируются по **заявленному значению ЧДД**. В финал проходят **20 %** допущенных к валидации, но **не более 10 команд**.

### Этап 2 — финальная проверка и защита

**Пересчёт ЧДД** (§ 4.4, § 6.4): организаторы запускают расчёт по предоставленным управляющим последовательностям. Если пересчитанное значение ЧДД **не совпадает** с заявленным — **дисквалификация**.

**Финальная защита** (§ 4.5) — онлайн, включает:

- краткую презентацию решения;
- демонстрационный запуск;
- ответы на вопросы жюри.

На защите оцениваются не только численные результаты, но и архитектурная проработка, обоснованность методов, качество реализации и способность подтвердить работоспособность системы.

Дополнительные процедурные детали (допуск по симуляторам, формат защиты), если они не закреплены в ТЗ, — в [submission.md](submission.md).

## Критерии оценки

### Первичный отбор (§ 6.2)

Основной количественный критерий — **величина ЧДД** на тестовом кейсе. Чем выше ЧДД, тем выше место в рейтинге. При одинаковых или близких значениях организаторы вправе применить дополнительные критерии по регламенту.

### Финальная оценка (§ 6.3)

Жюри учитывает совокупность:

- корректность и воспроизводимость решения;
- полноту учёта ограничений и условий задачи;
- техническое качество реализации;
- качество архитектуры и программной структуры;
- эффективность предложенного подхода;
- обоснованность выбранных алгоритмов и моделей;
- качество презентации и демонстрации;
- способность команды ответить на вопросы и подтвердить работоспособность.

## Контрольные точки

Контрольные точки предназначены для поэтапной проверки (раздел «Назначение контрольных точек» в ТЗ):

1. **Корректность выбранного направления** решения.
2. **Наличие работоспособного прототипа**.
3. **Готовность к финальной сдаче и защите**.

## Что нельзя

По ТЗ участникам **запрещено или не допускается**:

| Нарушение | Источник |
|-----------|----------|
| **Подмена исходных данных** собственными, если регламент не разрешает иное | § 5.2 |
| **Ручное вмешательство** в процесс расчёта после запуска | § 3.2.3 |
| **Скрытые зависимости**, неописанные внешние ресурсы, неконтролируемые параметры | § 3.5 |
| Генерация **некорректных или неполных** выходных файлов | § 3.2.3 |
| Заявление **несовпадающего с пересчётом организаторов** значения ЧДД на финале | § 4.4, § 6.4 |

Предоставленные материалы используются **исключительно** для выполнения задания в рамках хакатона (§ 5.2). Решение должно быть пригодно для проверки в среде организаторов, без привязки к специфической конфигурации оборудования участника (§ 5.3).

## Документация решения

Документация должна содержать (§ 3.7): назначение решения; описание архитектуры; порядок установки и запуска; сведения о входных и выходных данных; параметры и настройки; инструкцию по воспроизведению запуска на тестовом кейсе.

Ограничений по языкам программирования и библиотекам ТЗ не устанавливает, если организаторы отдельно не оговорили иное (§ 5.4). Рекомендуется использовать открытые и документированные инструменты (§ 3.6).
