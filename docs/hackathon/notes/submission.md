# Сдача и валидация (август 2026)

Правила отбора и проверки по [ТЗ §3.4–3.7, §4, §6, §8](../extracted/tz.md) и уточнениям организаторов (август 2026).

## Два этапа

1. **Первичный отбор** — автоматическая валидация на тестовом кейсе; ранжирование по заявленному NPV.
2. **Финал** — независимый пересчёт NPV организаторами + онлайн-защита с демонстрационным запуском.

## Валидационный кейс

На этапе валидации команда получает **тестовый (валидационный) кейс**: набор ограничений и историю разработки. Модели прежние — **Model Y** (трек 1) и **Model Z** (трек 2); меняются условия задачи, **не** само поле и не состав модели.

## Пакет для допуска к автоматической валидации

Обязательно ([ТЗ §3.4](../extracted/tz.md)):

1. исходные коды;
2. документация (см. ниже);
3. инструкция по развёртыванию и запуску;
4. файл конфигурации для воспроизведения;
5. **Docker-образ или материалы для сборки** — *при использовании контейнеризации* (онбординг рекомендовал Docker для воспроизводимости);
6. результаты запуска на тестовом кейсе: **`wells_schedule.inc`** и **заявленный NPV**.

Без полного пакета к валидации **не допускают**.

### Содержание документации ([ТЗ §3.7](../extracted/tz.md))

- назначение решения;
- архитектура;
- порядок установки и запуска;
- входные и выходные данные;
- параметры и настройки;
- как воспроизвести запуск на тестовом кейсе.

## Ключевые артефакты

- **`wells_schedule.inc`** — управляющий график, совместимый с ГДМ организаторов, **без ручного редактирования** после генерации ([ТЗ §3.2.3, §3.3.2](../extracted/tz.md)).
- **Заявленный NPV (ЧДД)** — по официальной методике **`CHDD_PYTHON`** ([npv.md](npv.md)).

Расчёт не должен требовать ручного вмешательства после старта.

## Процедура проверки организаторами (финал)

Для команд, прошедших в финал, организаторы выполняют **один полный прогон ГДМ** по сданному `wells_schedule.inc` и сравнивают **NPV** с заявленным.

- Расхождение заявленного и пересчитанного NPV — **дисквалификация** ([ТЗ §4.4, §6.4](../extracted/tz.md)).
- Допускается расхождение порядка **~2 %** из‑за различий симуляторов; это не считается ошибкой команды (уточнение организаторов).
- Выполняется **один расчёт**, повторные прогоны не предусмотрены.

## Рейтинг и финальная защита

**Первичный отбор** ([ТЗ §4.3, §6.2](../extracted/tz.md)):

- ранжирование по **заявленному NPV** на тестовом кейсе (чем выше — тем лучше);
- в финал — **20 %** допущенных к валидации, но **не более 10 команд** (по каждому треку / суммарно — см. регламент).

**Финальная защита** ([ТЗ §4.5, §6.3](../extracted/tz.md)):

- **7 минут** презентация + **5 минут** вопросы;
- демонстрационный запуск;
- жюри оценивает не только NPV, но и **архитектуру**, методы, реализацию, интерпретируемость, способность подтвердить работоспособность.

Итоговое место определяется подтверждённым NPV и оценкой жюри.

## Контрольные точки (КТ)

По разделу ТЗ «Назначение контрольных точек» — поэтапная проверка:

- корректность выбранного направления;
- работоспособный прототип;
- готовность к финальной сдаче и защите.

Календарь КТ — в регламенте и материалах организаторов.
