### 1.2. Два факта, определяющих проект

1. **На Model Z правила K4 и K5 несовместимы, пока обводнённость поля < 85 %.** При $B_o\in[0{,}998;1{,}0014]$, $B_w=1$, $R_s\approx0{,}005$ (`Model_Z_props.inc:6–18, 364–366`) пластовые объёмы равны поверхностным, и при закачке $=$ попутной воде

$$VRR=\frac{W_p B_w}{N_p B_o+W_p B_w}\approx f_w\quad\Rightarrow\quad VRR\ge0{,}85\iff f_w\ge0{,}85.$$

   В базе $f_w\le0{,}80$ даже в 2025 г.; ни один из 224 месяцев не допускает оба правила (R5 §2, A1 §0). Это не проблема кода — это пустое допустимое множество. Действие: вопрос организаторам сегодня (раздел 9, Фаза 0) и решение пользователя №1.
2. **База организаторов сама нарушает K2, K4, K5** (таблица выше). Значит «сравнимая база» для процентов должна быть определена заново, иначе любой допустимый кандидат сравнивается с недопустимой базой (раздел 10, решение №2).

### 1.3. Как ограничения входят в контур (репарация вместо штрафа)

Штрафы недопустимы: организаторы ранжируют по ЧДД без штрафов, нарушение — дисквалификация (R5 §5). Принцип: **входные границы — жёстко в самом расписании; выходные (K1, K2, K4, K5) — репарацией заданий по прогнозу и жёсткими воротами на пессимистичной квантили.**

Декодер политики (`policy_controls`, `propose_track2_policies.py:70–139`) дополняется двухпроходной репарацией по месяцам $m$:

$$s_L(m)=\min\Big\{1,\ \tfrac{(1-\varepsilon_L)\,1500}{\hat L(m)}\Big\},\qquad s_I(m)=\min\Big\{1,\ \tfrac{(1-\varepsilon_I)\,1500}{\hat I(m)},\ \tfrac{\varphi\,\hat W(m)}{\hat I(m)},\ \tfrac{1{,}15\,\hat V^{(3)}_p(m)}{\hat V^{(3)}_i(m)}\Big\},$$

где $\hat L,\hat I,\hat W$ — прогнозные среднемесячные жидкость, закачка и попутная вода (м³/сут) из прохода 1, $\hat V^{(3)}$ — трёхмесячные суммы пластовых объёмов (прокси 2.2); $\varepsilon_L,\varepsilon_I\in[0{,}02;0{,}05]$, $\varphi\in[0{,}85;1{,}0]$ — **наши** параметры отбора (запас под ошибку прогноза; калибруются по 90-му процентилю полевой относительной ошибки на банке, раздел 2.4). Это не «технологический запас сверх цифр» организаторов — их лимиты проверяются в точности, запас — правило нашего выбора. Проход 2 — прогноз с отмасштабированными LRAT/WRAT, затем ворота G2 на пессимистичных квантилях (верхняя q0,8 для $\hat L,\hat I$, нижняя q0,2 для $\hat W$). Стоимость: +1 прогноз (1,4 с) на кандидата; в поиске проход 1 берётся от инкумбента (3.3), проход 2 — только у элиты.

Нижняя граница VRR 0,85 репарацией недостижима (единственный «рычаг» — рост обводнённости). Она проверяется и отчитывается; статус «жёсткая/диагностическая» — поле профиля кейса, не код (решение №1).

## 2. Суррогат (TimesFM 3.0)

### 2.1. Что оставить как есть

Вход построен по API: один `predict_batch([targets], horizon=224, past_future_covariates=[cov], make_positive=True)` (`timesfm_economics.py:168–170`), контекст 128 = 4 патча, план управлений как past-future ковариата с lookahead 2 патча, без внешней нормализации, детерминизм (A2 §1.1). Девять целей достаточны для официального ЧДД без потерь (roundtrip). **Целевой набор не менять**: замена на «жидкость + обводнённость» не имеет измеренного преимущества (ошибка нефти $=\delta f_w/(1-f_w)$, нужна MAE обводнённости < 0,05 на 224 мес. — не показано ни в одном эксперименте, A2 §2.3), а `WVPT/WVIT` на Model Z выводятся из имеющихся целей с ошибкой < 0,2 % (2.2). Альтернатива в одну строку: при переобучении заменить `WEFF` (в ЧДД не входит) на `WVPT_Diff`, если организаторы подтвердят другой PVT.

### 2.2. Производные величины для ворот G2 (новая функция `derived_field_vectors`)

Из целей 7–9 и карты плотностей $\rho_{o,w},\rho_{w,w}$ по PVT-региону скважины:

$$\widehat{WWPT}_{w,m}=\frac{\text{WLPT\_Diff}_{w,m}-\text{WOMT\_Diff}_{w,m}}{\rho_{w,w}},\qquad \widehat{WOPT}_{w,m}=\frac{\text{WOMT\_Diff}_{w,m}}{\rho_{o,w}},$$

$$\hat V_p(m)=\sum_w\big[\widehat{WOPT}_{w,m}B_o+\widehat{WWPT}_{w,m}B_w\big],\qquad \hat V_i(m)=\sum_w\text{WWIT\_Diff}_{w,m}B_w,$$

$B_o=1{,}00$, $B_w=1$ (PVTO/PVTW дека; в базе $\Delta WVIT/\Delta WWIT=0{,}9995\text{–}1{,}0001$, R5 §1). Полевые агрегаты $\hat L,\hat I,\hat W$ — из тех же величин, делённых на $D_m$. Точность прокси проверяется на банке против `WVPT/WVIT` из SUMMARY (уже в `OPM_OPTIONAL_WELL_VECTORS`, `opm.py:60`) и записывается в квитанцию весов.

### 2.3. Квантили и пессимистичные ворота

`return_quantiles=True` (голова выдаёт 9 квантилей, `model.py`; сейчас отбрасываются, `timesfm_economics.py:170`). Ворота G2: K1/K2 по q0,8, K5 по q0,2 попутной воды; BHP по медиане (диагностика). Эти квантили не калиброваны (сообщество: покрытие 75,6 % при номинале 80 %, R3 §3) — калибровку по остаткам на банке делать в `evaluate_timesfm_scenarios.py`, результат — коэффициент расширения интервала в квитанции.

### 2.4. Данные: банк допустимых режимов (главная причина 58 % WAPE)

Веса 40 эпох, использованные в sealed-поиске, обучались только на сценариях с **сохранённой суммарной закачкой** (`scenario_generation.py:286–287, 301`); выбранный кандидат — закачка ×1,8 (A2 §0 п. 2). Новый режим «закачка ≤ попутная вода» означает закачку ≈ 0,3–0,6 от базовой — вне банка целиком. Новый банк (≈40 прогонов OPM 16 MPI × ≈4 мин, 2 воркера → 1,5–2 ч, A2 §4.4):

1. закачка $=\varphi\times$ попутная вода базы по месяцам, $\varphi\in\{0{,}7;0{,}85;1{,}0\}$ × производственный множитель $\{0{,}8;1{,}0;1{,}1\}$ — 9 прогонов;
2. то же + закрытие 5/10/20 самых обводнённых скважин — 6 прогонов;
3. переводы 1–3 скважин (есть готовый: скв. 104, `deliverables/conversion_search_20260910`) — 5 прогонов;
4. смена множителей во времени (месяцы 60/120) — 6 прогонов;
5. неоднородные per-well множители по блокам (LHS) — 8 прогонов;
6. уже посчитанные физические кандидаты с официальным ЧДД (+19,1 %, +19,05 %, +18,86 %, +1,24 %) — как обучающие, не как выборочные.

Каждый прогон — новый каталог, хэши, `check_summary` с новым профилем (K1–K5 по 1.1); frozen split: новые сценарии распределяются 70/15/15 по детерминированному хэшу имени; тестовые `physical-sweep [3,5,6]` и `fresh-uncertainty` остаются нетронутыми.

### 2.5. Обучение, оценка, ворота поддержки

- **До всего**: независимая оценка 60-эпоховых весов на `fresh-uncertainty` и `physical-z-forecast-validation --test-only` с `--gpu-memory-fraction ≥ 0,5` (OOM был при 0,35 с FP64-softmax 3,13 GiB, A2 §1.2 п. 10). Результат — число, а не предположение.
- **Multi-origin/random-window** (авторский рецепт дообучения, R3 §2.1): окна $(origin=t_0+k,\ horizon=224-k)$ из каждого train-сценария + исторические окна до 2007; тестовые сценарии не оконить (`finetune_timesfm_head.py:288–295, 377–392`). Это же покрывает «другую длину истории/горизонта» финального кейса.
- **Взвешивание потерь**: дисконт $1{,}1^{-t/12}$ по времени; вес целей ЧДД (`WOMT_Diff, WLPT_Diff, WWIT_Diff, WLPR`) выше `THP/WEFF`; агрегатный член по полевой сумме нефти (`pinball_loss`, :54–56, 299–304).
- **Метрика пригодности для выбора**: Spearman между прогнозным и официальным ЧДД по всем сценариям с OPM-ЧДД + смещение дисконтированной суммы нефти по полю. Критерий готовности весов: Spearman ≥ 0,8 на holdout, полевая WAPE нефти ≤ 10 % (цель; текущие dev-значения 12 % не независимы).
- **Ворота поддержки (OOD-guard)**: кандидат допустим, только если его сводные признаки (полевые/блоковые множители, число переводов/закрытий, $\varphi$) лежат в выпуклой оболочке обучающих сценариев (+10 % расширения); фиксируется в записи кандидата рядом с `forecast_eligible` (:428–430). Это trust-region без OPM в цикле (R1 §d).
- Детрендинг (`use_linear_detrending=True`, экстраполяция тренда на 1,75 контекста) — одно ablation-обучение; без измерения не отключать.

### 2.6. Горизонт 224: не делить

Direct-224 остаётся: это штатный режим 3.0 («entire horizon in a single forward pass», https://research.google/blog/timesfm-3-a-zero-shot-foundation-model-for-multivariate-forecasting), 1,4 с на кандидата, ноль OPM в поиске. Разбиение на окна с собственными прогнозами в контексте разрешено правилами (наблюдений нет), но zero-shot дало 161,9 % WAPE (`docs/ALGORITHM_TRACKS_1_2.md:807–813`), а авторы убрали авторегрессию из-за накопления ошибки; разбиение с новыми наблюдениями (5,6 %) запрещено контрактом печати. Замысел организаторов — агенты управляют всем оставшимся периодом от даты X, значит прогноз обязан покрывать весь период. Chunked-decode — только как дешёвый эксперимент на frozen-наборе с готовыми весами (0 OPM), не как замена. Правило «1545 вариат при `max_variates: 32`» оставить (веса дообучены под него); «группы ≤ 32» — эксперимент Фазы 3+ (A2 №12).

Ожидаемая ошибка после Фазы 3 — неизвестна до измерения; честная граница: если Spearman < 0,6, поиск по суррогату не имеет смысла и это будет доложено как результат.

## 3. Поиск

### 3.1. Выбор: правило-ориентированная иерархическая политика + CMA-ES с репарацией, LLM-затравкой и LLM-инъекциями

Почему: чёрный ящик ≈1,4 с (после ускорений раздела 5), непрерывные коррелированные параметры, бюджет ≈300–500 оценок за 10 мин, жёсткие ограничения через репарацию — режим, где CMA-ES доминирует (Nevergrad: «CMA лучший для control при большом бюджете», https://facebookresearch.github.io/nevergrad/optimization.html; Beykal 2025 — суррогат + PSO/CMA-ES при 1 769 ограничениях, https://pmc.ncbi.nlm.nih.gov/articles/PMC12007002). Библиотека: `cma` 4.4.x (PyPI 4.4.4 на 11.09.2026, https://pypi.org/project/cma/; BSD-3, только numpy; ask/tell, `inject`, опция `seed`, `bounds`). Отвергнуто в одну строку: **DE/NSGA-II (pymoo/nevergrad)** — нужны ≥1 000 оценок при dim > 100; **BoTorch SAASBO** — оправдан только при последовательном калькуляторе (≤200 оценок), а калькулятор распараллеливается; **DRL** — 10⁵ симуляций; **LLM как оптимизатор чисел (EvoLLM)** — проигрывает CMA с ростом dim (https://arxiv.org/html/2402.18381v1); **текущая сетка 8 точек + 3 раунда Qwen** — 11 оценок за 18,5 мин. Без новой зависимости: `scipy.optimize.differential_evolution(vectorized=True, constraints=NonlinearConstraint, seed=…)` (scipy 1.18.1 уже в `uv.lock`) — вдвое хуже по сходимости на этом бюджете, но работает.

### 3.2. Параметризация ($x\in[0,1]^{18}$, декодер → существующая схема `policy`)

| Группа | Параметров | Смысл |
|---|---|---|
| Полевой множитель добычи по двум половинам периода | 2 | $[0{,}6;1{,}2]$ |
| Доля попутной воды на закачку $\varphi$ по двум половинам | 2 | $[0{,}7;1{,}0]$ — заменяет `injector_scale`, который под K5 бессмыслен |
| Блоковый множитель добычи (6 блоков Ward, 4.1) | 6 | $[0{,}5;1{,}3]$ |
| Блоковые доли закачки (нормируются в сумме к 1) | 6 | перераспределение воды между блоками по связности |
| Порог обводнённости закрытия (одноразово, без повторного пуска) | 1 | $[0{,}90;0{,}995]$ |
| `producer_bhp_add` | 1 | $[0;30]$ бар |

Дискретные гены (не в $x$): списки закрытий/переводов и per-well override от блоковых агентов; генный набор фиксирован на протяжении «эпохи» CMA и меняется только LLM-инъекцией (3.4). Декодер: $x$ + гены → `policy` (`producer_scale`, `well_scales`, `well_updates` по интервалам, `shut_wells`, `producer_bhp_add`) → `policy_controls` (:70–139) → репарация 1.3 → `CycleRequest`. Многомасштабный принцип (поле → блок → скважина) — Lien/Jansen 2008, Oliveira/Reynolds 2015 (R1 §b).

### 3.3. Цикл и бюджет

```
seeds = LLM round 0 (≤8 политик) ∪ Sobol(32, dim=18, seed=20260909)   # scipy.stats.qmc.Sobol
оценить seeds (2 прохода репарации у каждой); x0 = лучший допустимый
es = cma.CMAEvolutionStrategy(x0, 0.25, {'seed': 20260909, 'bounds': [0,1], 'popsize': 12})
while wall_clock < 10 мин:
    X = es.ask()                          # 12 векторов
    policies = [decode(x, genes, aggregates_of_incumbent) for x in X]   # проход 1 — от инкумбента
    forecasts = gpu_forecast(policies)     # 12 × 1,4 с, последовательно; B=2 если память
    scores = cpu_pool.map(score, ...)      # калькулятор в процессе, 8 воркеров
    es.tell(X, fitness)                    # fitness = −ЧДД(медиана) для допустимых; недопустимые — ранжируются по сумме нарушений ниже всех допустимых (feasibility-first)
    if gen % 8 == 0 and injections < 3: es.inject(LLM-инъекция(elite_digest))
top-5 → второй проход репарации + пессимистичные ворота → элита для seal
```

Оценки: поколение ≈ 17 с GPU + CPU внахлёст ≈ 20 с; 10 мин → ≈28 поколений ≈ 340 оценок + 40 затравок ≈ 380 кандидатов. Допустимость: репарация делает K1/K2/K5 выполненными по построению на прогнозе; ворота G2 на квантилях + OOD-guard + «пессимистичный прирост» ($\text{ЧДД}_{q0{,}3}$ кандидата ≥ прогнозный ЧДД базы, обе величины — официальным калькулятором в процессе) определяют `forecast_eligible`. Печать (`seal_forecast_selection`) без изменений: argmax официального прогнозного ЧДД среди допустимых.

### 3.4. Участие агентов в переборе (требование организаторов)

- **Раунд 0** (до CMA): 6 блоковых планировщиков параллельно → `BlockIntent` (дискретные гены + диапазоны блоковых множителей); глобальный планировщик → ≤8 полных политик-затравок + сужение коробки для $x$. Это warm-start в духе LLAMBO (https://iclr.cc/virtual/2024/poster/18743).
- **Инъекции** (≤3, каждые 8 поколений): глобальный планировщик получает дайджест элиты (топ-8: расшифрованная политика, ЧДД, запасы K1–K5, вклад блоков по leave-one-block-out из прогноза) → ≤4 новых кандидата как типизированные правки инкумбента (новый генный набор) → оцениваются и `es.inject`. Это дискретный оператор мутации в духе LMEA/EvoPrompt (https://arxiv.org/html/2309.08532v3), числа считает CMA-ES.
- **Критик** — после печати, по квитанциям и слою интерпретируемости; только вето.

Все предложения LLM проходят те же валидатор, репарацию и ворота; ни одно решение о допустимости или выборе LLM не принимает (контракт трека 2, R2 §2).

### 3.5. Что убрать

Три раунда по 4–5 вызовов с ≈101 k символов (≈72 k токенов, A3 §1) на роль; координатор и аналитик как отдельные полевые роли (оба рекомендуют `propose_policy`, `first-agent-plan.json`); инструмент `propose_policy` с исполнением `evaluate` внутри LLM-вызова (конкурентный доступ к GPU и `candidates`).

## 4. Топология агентов

### 4.1. Блоки

В деке Model Z **нет разломов**: `FAULTS/MULTFLT/THPRES/MULTREGT` отсутствуют, `MULTZ 547638*1`, все 103 скважины в одной группе `'GROUP'`, `source_faults_present: false`, граф связности — одна компонента (A3 §2, R2 §0). Структура вертикальная: два объекта `FIP_C1` 1/2 (SATNUM/PVTNUM 1/2), 23 скважины вскрывают оба. Блоки — проектное решение: **Ward-кластеризация координат $(i,j)$ из `WELSPECS`, k=6**, `scipy.cluster.hierarchy.linkage(..., 'ward')` при фиксированном порядке `well_ids` — детерминирована; 99,1 % веса связности внутри блоков, 75 % «пяти сильнейших соседей» внутри блока (A3 §2, таблица 103 скважин там же). Разбиение пишется в `blocks.json` (хэш `connectivity.json`, параметры, граничные пары) и в `proposal-receipt.json`. Для K6 «давление по блокам»: уровень 1 — `FIP_C1`/`FIP_ZONE` из дека (наиболее вероятный объект проверки организаторов), уровень 2 — среднее `WBP9` по Ward-блокам.

## 7. Детерминизм и воспроизводимость

- **Численный путь** (TimesFM → калькулятор → seal) детерминирован на том же GPU/torch/CUDA: `use_deterministic_algorithms`, math-SDPA, `CUBLAS_WORKSPACE_CONFIG=:4096:8`, `manual_seed(20260909)`, FP64 variate-softmax (parity 0.0, `precise-attention-check.json:9–10`), `PYTHONHASHSEED=0` в калькуляторе. Добавить в квитанцию `torch.__version__`, CUDA, драйвер, имя GPU, `forecast_batch_size`; seed CMA-ES = 20260909; порядок оценок — батчи фиксированного размера, id до отправки в пул.
- **LLM-путь** побитово не гарантируется ни одним эндпоинтом (Cerebras: best-effort; batch-invariance у Qwen3-235B — 80 уникальных ответов из 1000 при T=0, https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference). Достижимо: воспроизводимость **по данным** — все предложения LLM это хэш-адресуемые JSON, всё после них детерминировано. Обязательно: `llm_calls.jsonl` с `request_sha256`, `messages_sha256`, `response_sha256`, `content/reasoning/tool_calls_sha256`, `system_fingerprint`, `finish_reason`, `usage`, `time_info`, `attempt`/HTTP-статус; флаг `--replay <dir>`, подменяющий клиент чтением сохранённых ответов; N=3 повторов контекста → `llm_variance.json` (доля совпавших `controls_sha256`).
- **Убрать неповторяемость из хэшей**: `inference_seconds` вынести из `record` в `timing-XX.json` (сейчас попадает в `request_sha256` и в промпты full-cycle, `propose…:391, 421, 434`; `workflow.py:838–848`); `sealed_at_utc` и OPM-манифесты сравнивать по объявленному списку полей, не по хэшу файла.
- **Протокол приёмки** (A6 §4): (1) два поиска с одним seed — сетка/Sobol/затравки обязаны совпасть побитово по `controls_sha256, forecast_sha256, forecast_chdd_m`; раунды LLM — по `llm_calls.jsonl` локализуется первый разошедшийся `call_index`; (2) один вызов Cerebras N=10 для `high`/`none` и structured — уникальных `content_sha256` (критерий: 1 для JSON при фиксированном `system_fingerprint`); (3) OPM 1×1 ×2, 1×2 ×2, 16×1 ×2 — SHA `canonical/chdd.csv`, `summary-report.txt`, `economics-*/result.json` (≈1,5 ч CPU).
- **Режим OPM**: 16 MPI даёт −0,006 % ЧДД, но до 24,37 бар локально по BHP (`docs/A100_PERFORMANCE_20260909.md:38–48`) — для K3 это риск ложного «прошёл». База и кандидат — всегда в одном режиме; в `final-audit.json` — `command` обеих сторон и минимальный запас по BHP; если запас < 25 бар — прогон подачи повторить в 1×1 (решение №3).
- Бандл организаторам: `request-XX.json` победителя, overlay + `schedule_overlay_sha256`, `selection-before-opm.json`, `full-cycle-receipt.json`, `canonical/chdd.csv`, `economics-*/{input.csv,result.json,manifest.json}`, режим OPM, `llm_calls.jsonl`, SHA весов + `report.json`, `case_constraints.json`, `blocks.json`.

## 10. Риски для цели +70 % и честная оценка

1. **Опубликованные приросты от управления заводнением — 4–33 %** (EnOpt +4,2 %, PSO/CMA-ES на суррогате +10,7 %, DRL +15–33 % при 10⁵ симуляций, streamline-перераспределение +20–29 %; R1 табл. a). +70 % нигде не документирован. Наш лучший физический кандидат — +19,1 % при закачке до 2 117 м³/сут и без K1/K2/K4/K5.
2. **Что должно быть верно для +70 %**: (а) сравнимая база сама ограничена теми же правилами (K5 режет её закачку с ≈1 712 до ≤ 738 м³/сут — средняя попутная вода — и ЧДД базы существенно падает; относительный прирост умной аллокации тогда может быть большим, но абсолютный — нет); (б) большие ранние выигрыши (дисконт 10 %: первые 5 лет ≈ 45 % веса) за счёт закрытия убыточных обводнённых скважин (фонд 1 млн/год, 100 руб./т жидкости) и переноса квоты 1500 м³/сут на низкообводнённые; (в) структурные рычаги (переводы, закрытия) — те, которых нет в банке и которые суррогат сейчас предсказывать не умеет. Против **неограниченной** базы 11 873,62 млн: +70 % ≈ +8,1 млрд дисконтированных руб. ≈ +2,5 млн т нефти при зажатой жидкости, т.е. падение обводнённости с ≈0,6 до ≈0,35 (A1 §4 п. 9, A2 §4.3) — управлением не достигается; при этом K5 отнимает пластовую энергию и сам кандидат, скорее всего, окажется **ниже** неограниченной базы.
3. **Лимиты 1500/1500 и коридор делают цель менее правдоподобной**: K1 почти не связывает (56/224 мес), K2 при K5 «мёртв» (закачка ≤ $f_w\cdot1500<1500$), K5 связывает жёстко, K4 (нижняя) невыполним до $f_w\ge0{,}85$. Задача превращается из масштабирования в распределение квоты воды и жидкости — там приросты в литературе десятки процентов к плохой базе, единицы к хорошей.
4. **Ошибка суррогата**: sealed-кандидат — 58 % WAPE нефти, прогнозный ЧДД +39,6 % против физических +8,5 %; новый режим — OOD для всех текущих весов. Без Фаз 2–3 любой поиск оптимизирует ошибку модели. Защиты: OOD-guard, пессимистичные квантили, пессимистичный прирост, репарация; при Spearman < 0,6 на holdout — доклад «поиск по суррогату непригоден».
5. **Правила проверки**: BHP «на каждом шаге» ловит переходные выбросы, которые есть у самой базы (38,98/388,2 бар); 16 MPI даёт до 24 бар локального разброса; определение VRR/окна и статус базы не подтверждены письменно. Каждый из этих пунктов может дисквалифицировать результат независимо от его величины.
6. **Оценка достижимости**: против неограниченной базы — практически недостижимо (< 5 % субъективной вероятности); против базы с теми же ограничениями — неизвестно, определяется тем, насколько плоха «наивная» ограниченная база; +15–25 % к ограниченной базе — реалистичная цель при удавшейся Фазе 3. Результат ниже цели — это результат, а не повод менять правила отбора.

## Приложение. Решения, требующие владельца

1. **Как трактовать нижнюю границу VRR 0,85 на Model Z, где при закачке только попутной воды VRR = обводнённость (< 0,85 во все 224 месяца учебного кейса)?**
   - (a) Жёстко везде: профиль с lower_bound_status=hard; на учебном кейсе ожидается ноль допустимых кандидатов, и это докладывается как результат
   - (b) Жёстко в профиле тестового кейса, диагностически в профиле разработки (lower_bound_status=diagnostic) до письменного ответа организаторов; водный баланс и верхняя граница 1,15 — жёстко всегда
   - (c) Считать VRR как закачка/добытая вода (denominator=water_surface), полагаясь на фразу «компенсация около 1» из п. 2 организаторов
   Рекомендация: (b) плюс письмо организаторам сегодня (вопросы Фазы 0); (c) применять только после их подтверждения, (a) — если ответ «оба правила жёсткие»

2. **С какой базой сравнивать ЧДД, если база организаторов сама нарушает лимит закачки, коридор VRR и водный баланс?**
   - (a) Неограниченная база организаторов как есть (11 873,62 млн) — +70 % практически недостижим, кандидат под K5 скорее всего ниже базы
   - (b) Репарированная база: тот же исходный график с закачкой, зажатой попутной водой и лимитами по фактам базового OPM, один парный OPM-прогон (≈7,6 мин), согласовать с организаторами
   - (c) Только спросить организаторов и ждать
   Рекомендация: (b): подготовить репарированную базу и одновременно спросить; отчитывать оба процента (к неограниченной и к репарированной базе) до ответа

3. **Режим финального OPM для sealed-прогона и парной базы.**
   - 16 MPI × 1 поток: ≈3,6 мин, ЧДД −0,006 %, локальный разброс BHP до 24 бар; плюс обязательный аудит запаса по BHP 50/300
   - 1 MPI × 1 поток: ≈20–25 мин (оценка), побитово повторяемо (проверить протоколом 4.3); полный сеанс ≈40 мин
   Рекомендация: 16×1 для репетиций и банка; для прогона подачи — 16×1, если минимальный запас по BHP на репетиции ≥ 25 бар, иначе 1×1

4. **Переход на Cerebras Developer tier для Qwen 3.8 27B (покупка от $10, ключ в runtime-файле на A100, проверка только через test -s).**
   - Cerebras Developer: reasoning high, ≈$0,15–0,30 за сеанс, ≈3–5 мин LLM вместо 16,7; детерминизм best-effort
   - Остаться на litellm.tatneft.guru: без reasoning_effort/seed-гарантий, ≈5,5 мин на раунд при старом контексте; с новой топологией тоже быстрее, но латентность не измерена
   Рекомендация: Cerebras Developer как основной эндпоинт, Tatneft — резервный путь в том же коде (переключение переменными окружения)

5. **Добавить зависимость cma (pycma 4.4.x) для CMA-ES или ограничиться scipy (differential_evolution vectorized + Sobol), уже присутствующим в uv.lock?**
   - Добавить cma: лучшая сходимость на dim 18 при ≈400 оценках, ask/tell/inject, BSD-3, только numpy
   - Только scipy: без новой зависимости, ожидаемо хуже сходимость на этом бюджете, нет inject для LLM-затравок (эмулируется через init population)
   Рекомендация: Добавить cma через uv (uv add cma, uv sync --locked), scipy-путь оставить как задокументированный fallback за флагом
